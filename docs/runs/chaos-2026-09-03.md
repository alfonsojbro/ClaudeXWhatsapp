## What each scenario exercised

### 1 — baseline

All three stubs healthy: bridge on 17801 (`ok: true, connected: true`), brain on 17802, Google
token stub on 17803 returning `access_token`. `cxw-ops health` ran with every check green and
exited 0. No `[alert:` line appeared, which proves the reconcile step does not alert on a first
healthy run.

The scenario then runs `monitor.sh` once and asserts `$CXW_STATE_DIR/monitor.status` starts with
`ok`. That assertion exists because a green box used to write `fail` there: `problem_count()` ran
`grep -c … || echo 0`, and on an empty problem list `grep -c` printed `0` **and** exited 1, so the
`||` appended a second `0` and every `[ "$count" -eq 0 ]` test errored into the failure branch.

### 2 — bridge down: the fallback channel and the self-heal

**Killed:** the bridge stub, by `kill $(cat $STUB_DIR/bridge.pid)`.

Five things were checked in one scenario:

- The `whatsapp` check failed, so the alert did **not** go through WhatsApp. It went to the email
  channel — `[alert:email] … whatsapp FAILING`. The run also asserts the absence of an
  `[alert:whatsapp]` line for that alert. This is the case the fallback chain exists for: the
  most likely single failure is also the primary alert channel.
- `monitor.sh` emitted `HEAL restart bridge`.
- **Heal fired:** `fake-ctl.sh` logged `restart bridge` and respawned the bridge stub, standing in
  for `sudo -n cxw-ctl restart bridge` → `systemctl restart cxw-bridge`.
- The next `cxw-ops health` produced `[alert:whatsapp] … whatsapp recovered` — the recovery
  message came back over WhatsApp because that channel was healthy again.
- `monitor.status` reads `ok` after the post-heal re-check, i.e. the monitor clears its own
  failure signal once the heal works, rather than leaving a stale `fail` for the operator.

**Channels:** failure on email, recovery on WhatsApp.

### 3 — Google token unplugged

**Toggled:** `STUB_GOOGLE_FAIL` created, which makes the Google stub answer `POST /token` with
401 `invalid_grant`; then removed to restore it.

The `google` check failed and recovered. Both alerts went out over WhatsApp
(`[alert:whatsapp] … google FAILING`, then `… google recovered`) because the bridge was healthy
throughout. **No heal fired** — the `google` check has no heal action by design; a bad refresh
token needs a human (RUNBOOK §12.1).

### 4 — disk pressure and the emergency purge

**Toggled:** `CXW_DISK_LIMIT_PCT=0` for one `monitor.sh` run, so "used ≥ 0 %" always fails.

- `monitor.sh` emitted `HEAL purge --emergency`.
- **Heal fired:** the monitor ran `cxw-ops purge --emergency` against the seeded database and then
  `fake-ctl vacuum-journal`. The purge JSON reported `mediaRows=3`.
- **Retention held:** all 3 third-party media files were deleted and the 1 owner media file
  survived (`owner files=1, third-party files=0`). This is the `CXW_RETENTION_OWNER_FOREVER`
  guarantee under the emergency path, which is media-only and never touches text.
- With the override removed, the following `cxw-ops health` exited 0 — the check recovered.

### 5 — alert dedupe

**Toggled:** `STUB_GOOGLE_FAIL` again, then three consecutive `cxw-ops health` runs.

Exactly one `[alert:` line across all three. `CXW_ALERT_REPEAT_MIN=999` in the chaos environment,
so the repeat window never opens during the run. This proves the `alerts.json` state machine does
not re-alert on every tick of a continuing outage.

### 6 — the monthly cost cap

**Seeded:** one row in the throwaway `ops.sqlite` `usage` table with `cost_usd = 0.02`, stamped
`Date.now()`, written with `node:sqlite`. `cxw-ops costs check` then ran twice with
`CXW_COST_MONTHLY_CAP_USD=0.01`, i.e. the month is over cap.

- The first check produced exactly one `[alert:` line, and its text mentions the cost cap
  (`🛑 cxw: monthly cost cap reached …`). This is the path the monitor drives every 10 minutes.
- The second check produced **no** alert line: the `cost-paused-alerted-<YYYY-MM>` marker makes
  the notification once per month per level.

**No heal fired** — a cost cap is not a fault. The check also writes `state/cost-paused`, which is
what makes the scheduler skip non-essential routines.

## Deviations from the plan

1. **`CXW_DISK_LIMIT_PCT=100` in the base chaos environment.** The plan (§I2) only specified
   `CXW_DISK_LIMIT_PCT=0` for scenario 4. The dev Mac's real disk is 90.4 % used, over the 85 %
   default, so without a base override scenarios 1, 2, 3 and 5 would have failed on the `disk`
   check for a reason unrelated to what they test. `100` means "alert when used ≥ 100 %", i.e.
   never. Scenario 4 still overrides it to `0`. The override is commented in `chaos.sh`.
2. **`chaos.sh --box` was not run.** There is no Hetzner box yet, and Phases 1–5 are not built,
   so there is nothing on a box to kill. The `--box` path is guarded twice (`--i-know` plus a
   root check) and restores in a trap, but it is unexecuted code.
3. **Everything is stubs.** No Baileys session, no Agent SDK, no real Google endpoint, no
   `systemctl`. `fake-ctl.sh` stands in for `cxw-ctl`, and `CXW_ALERT_TRANSPORT=log` means every
   channel "accepts" and prints instead of sending, so channel _selection_ was verified but
   channel _delivery_ (real SMTP, real Telegram, real `POST /send`) was not.
